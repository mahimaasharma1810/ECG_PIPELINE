# Audit — 2026-07-31

This file captures a specific trust/correctness question raised about the
VitalPatch ECG pipeline's R-peak detection and its effect on the reported
CRITICAL rate. It is not a full pipeline audit — just this one thread,
recorded so the finding and its evidence don't get lost.

## 7. Trust question: is R-peak detection accurate, and how much of the CRITICAL rate was an artifact?

**Short answer:** a real bug was found and fixed. The old CRITICAL rate
(290/2889 = 10.0%, matching `Docs/CLINICIAN_REVIEW_INSTRUCTIONS.md`) was
substantially inflated by R-peak over-detection. The corrected rate,
measured by re-scoring all 2,889 assessable segments, is **15/2889 =
0.5%** — a ~94.8% reduction in CRITICAL calls. See "Full-corpus impact"
below for the complete before/after breakdown.

### What was wrong

`detect_r_peaks()` (`ecg_pipeline/ecg_pipeline_core.py`, mirrored in
`ecg_inference/detector.py`) used WFDB's `XQRS` detector with default
config. `XQRS.Conf.t_inspect_period` — the parameter that enables XQRS's
own built-in T-wave-vs-QRS slope check — defaults to `0`, which disables
that check entirely. On this device's ECG morphology, a candidate peak
that clears the 200ms hard refractory period and the amplitude threshold
was accepted as a second, spurious beat regardless of whether it was
actually a T-wave.

Verified directly on patient 1844AC, segment
`1778227671297_VC2B008BF_1844AC_ecg_seg0`: true beat count (cross-checked
against the independently-measured vitals HR, 76.3 bpm over 116.8s ≈ 149
beats) was being reported as up to 244 detected beats by the unfixed
detector on that segment in earlier testing — roughly 1.6-2x — with the
RR-interval sequence showing the characteristic alternating short/long
pattern of a real beat immediately followed by its own T-wave being
counted as a second "beat" (fake bigeminy). This inflated HR, PVC/AFib
burden calculations, and fed directly into the risk cascade — HR ~105
bpm and a CRITICAL verdict on 1844AC's segment 0 before the fix, vs. HR
~70.5 bpm (within a few % of the vitals-measured 76.3) and HIGH after.

### What was fixed

1. **`detect_r_peaks`**: set `Conf(t_inspect_period=0.36)` (the
   conventional Pan-Tompkins-style T-wave-inspection window), enabling
   XQRS's existing, designed-for-this check. Applied identically in both
   `ecg_pipeline_core.py` and `ecg_inference/detector.py`.
2. **`_apply_refractory_guard`** (new function, both files): a
   physiological refractory-period guard applied after detection + snap
   — no two accepted R-peaks within 200ms of each other; when two survive
   that close, the larger-|amplitude| one on the filtered signal is kept.
   Standard, detector-agnostic safety net. Note: since T-waves on this
   device typically land ~250-400ms after the R-peak (outside a 200ms
   window), this guard's practical contribution here is small relative to
   fix #1 — its value is as a defense-in-depth catch for the sub-200ms
   case, not the primary fix.

Neither change touches the XQRS algorithm choice, the Kalman filter, the
classifier weights, or any risk threshold — confirmed by inspection and
by the fact that all 5 synthetic ground-truth scenarios
(`ecg_pipeline/test_pipeline_synthetic.py`, including the VT_RUN fast-rate
case) still pass unchanged.

### What was investigated and explicitly rejected (measured, not assumed)

A second hypothesis was raised: that the *snap-to-local-peak* step
(`_snap_to_local_peak`, search radius 15 for VitalPatch) was
mis-locating peaks onto T-waves/baseline rather than only over-counting
them. This was measured, not assumed, using an independent slope-based
QRS locator (unrelated to XQRS) across the same 5 segments as ground
truth:

- **Snap target (positive-only vs. current `abs()`-based)**: rejected.
  Direct measurement on 1844AC shows ~10% of correctly-placed peaks have
  *negative* signed value at the true QRS location — consistent with
  genuine PVC beats, which are clinically expected to have inverted
  polarity. Patient 184B27's QRS complex is negative-going for
  essentially every beat (visually confirmed, see below) — forcing
  positive-only detection would break detection entirely for that
  patient. `abs()`-based selection is correct for a pipeline whose job
  includes detecting PVCs.
- **Snap radius (10 or 8 instead of 15)**: rejected. Narrowing the radius
  strictly *increased* mis-detection against the independent locator
  (0.9% → 2.0% → 5.5% as radius shrank from 15 → 10 → 8), consistent with
  the existing documented 13-record MITDB sweep that originally set
  radius=15 for non-WFDB sources.
- **Steepness-based tiebreak for near-amplitude-tied candidates** (e.g. a
  negative T-wave trough within ~10% of the true R-peak's |amplitude| —
  one real instance found and confirmed on 1844AC, R=+24.0 vs a T-trough
  90ms later at -24.1): implemented, then measured against the
  independent locator across all 5 segments — it scored **worse**
  overall (77/933=83.3% peaks correctly on the true QRS vs. 848/933=90.9%
  with plain `abs()`-argmax), regressing 3 of 5 segments including one
  from 100%→78%. **Reverted.** Documented in
  `_snap_to_local_peak`'s docstring as a negative result so it isn't
  re-attempted without re-measuring.

Net: the snap logic is unchanged from before this audit. The residual
known gap is a small number of beats on patient 1844AC specifically
where the true R-peak and a nearby T-wave have near-tied |amplitude| —
visually confirmed (2 of 13 beats in a 10s window landed on the T-wave
trough instead of the adjacent true R-spike). This is a real, narrow,
unresolved limitation — not eliminated, but also not fixed by either
attempted approach, and left as a documented open item rather than
papered over.

### Visual confirmation

Two 10-second strips (20-30s window) were regenerated with current
detection overlaid:

- **184B27**: 20/20 beats correctly dotted on the true (negative-going)
  QRS spike, none on baseline/T-wave, none missing. Clean.
- **1844AC**: 11/13 beats correctly dotted on the true (positive-going)
  R-spike; 2/13 landed on a negative T-wave trough of near-equal
  amplitude to the true R-peak (see rejected-fix note above). No
  double-counting (no two dots per beat) — the over-detection/fake-
  bigeminy problem from before the fix is gone; the residual issue on
  this patient is now purely the rarer per-beat mis-snap, not counting
  every beat twice.

### Full-corpus impact

Full 2,889-segment assessable-corpus re-score (t_inspect_period fix +
refractory guard, snap logic unchanged vs. the saved baseline in
`vitalpatch_run_manifest.csv`), scoring only (no report regeneration).
0 errors, 2889/2889 scored.

**By original (saved/pre-fix) risk level, where it landed after the fix:**

| pre-fix level | n (pre-fix) | -> LOW | -> MEDIUM | -> HIGH | -> CRITICAL | -> NOT_ASSESSABLE |
|---|---|---|---|---|---|---|
| LOW | 1881 | 1372 | 3 | 503 | 0 | 3 |
| MEDIUM | 166 | 43 | 113 | 3 | 0 | 7 |
| HIGH | 552 | 101 | 6 | 432 | 0 | 13 |
| CRITICAL | 290 | 198 | 19 | 41 | 15 | 17 |

**Post-fix totals:** LOW 1714, MEDIUM 141, HIGH 979, CRITICAL 15,
NOT_ASSESSABLE 40 (sums to 2889).

**Headline:** CRITICAL 290 (10.0%) -> 15 (0.5%). Of the 290 segments
previously called CRITICAL, 198 (68%) are now LOW and only 15 (5%)
remain CRITICAL — consistent with the over-detection bug's mechanism
(inflated HR / fake short-RR runs feeding the PVC-burden and VT-run
rules that dominate the CRITICAL cascade).

**Not yet fully explained — flagged, not swept under the rug:**
LOW->HIGH accounts for 503 segments, the single largest transition in
either direction. This is *not* simply "false positives corrected" —
it's segments the old (buggy) pipeline called LOW that the fixed
pipeline now calls HIGH, i.e. newly-elevated, not newly-lowered. Spot
evidence from the 5-segment test set is consistent with at least some
of this being real, previously-masked findings rather than a new bug:
patient 183594's segment 0 flipped LOW->HIGH, and the independently-
computed multimodal manifest (`multimodal_batch/multimodal_manifest.json`)
already had that same segment flagged `has_afib: True` /
`afib_burden_pct: 50.0` via a separate computation path — i.e. the
fixed ECG-only pipeline is now agreeing with an independent AFib signal
it previously disagreed with, not diverging from it. A plausible
mechanism: the old bug's regular, alternating (bigeminy-like) double-
counting made RR intervals look artificially *regular*, which can mask
genuine AFib-type irregularity from a burden/variability-based rule.
This is a reasonable hypothesis, not a proven one — a full explanation
of all 503 would need per-segment review, which hasn't been done. Flag
this explicitly before treating the corrected numbers as a clean,
one-directional "false positive reduction" story.

### Constraints honored

- XQRS was not swapped for a different detector.
- The Kalman filter and classifier weights were not touched.
- No risk threshold was adjusted to compensate for anything — the fix is
  entirely in detection, upstream of scoring.
- The fix was applied identically to `ecg_pipeline_core.py` and
  `ecg_inference/detector.py`, and the shared synthetic ground-truth
  suite still passes on both.

## 8. Follow-up fixes found while regenerating clinician-review material (same day)

Two smaller, real bugs surfaced while updating
`Docs/CLINICIAN_REVIEW_INSTRUCTIONS.md` for the corrected 15/2889 count
above, plus one display-only fix for the waveform PNGs. All three are in
`ecg_pipeline_core.py`, `ecg_pipeline/agent_bridge.py`, and
`ecg_pipeline/generate_clinician_report.py`.

### 8.1 SDNN's "not enough data" case was silently sentinel-valued as 0.0

`recording_level_hrv()` (`ecg_pipeline_core.py`) returned
`sdnn_ms: 0.0` whenever fewer than 3 valid RR intervals were available —
the same dict shape as a real measurement. `score_recording()` then did
`hrv_suppressed = sdnn_ms < thresholds.hrv_sdnn_suppressed_ms`
(threshold 20.0ms). Since `0.0 < 20.0` is always true, every segment
with too little RR data to say anything about HRV was silently scored
as **MEDIUM ("Sustained HRV suppression")** — a real risk-level
distortion, not just a cosmetic display issue, on the segments this
condition affects.

**Fix:** `recording_level_hrv()` now returns `sdnn_ms: None` for the
too-little-data case; `score_recording()` treats `None` as "rule cannot
fire" (`hrv_suppressed = sdnn_ms is not None and sdnn_ms < threshold`),
never as a value that happens to satisfy `< threshold`.
`agent_bridge._build_rule_trace()` displays this case explicitly as
`"not evaluated (<3 valid RR intervals)"` rather than a bare number a
reviewer could mistake for a measured zero.

**Not yet mirrored — open bug, not fixed:** `ecg_inference/` (the
deployment package `run_inference.py` uses) has its own copies of this
logic in `ecg_inference/features.py` and `ecg_inference/classifier.py`,
and neither was updated. The 0.0-sentinel bug described above is
**still live in the deployment path** as of this writing. This breaks
the dev/inference equivalence this project otherwise maintains
(`Docs/inference_ready.md`) and should be fixed before the next
inference-package equivalence check. See README "What to fix next."

### 8.2 Waveform PNGs were unreadable — Kalman EMG-suppression assumes the wrong signal scale

`recompute_filtered_signal()` (`generate_clinician_report.py`), used
only to draw the waveform panels in clinician reports, ran the full
filter chain including the final Kalman EMG-suppression step
(`emg_suppress_kalman`). That step's `process_var`/`meas_var`
constants are fixed absolute values tuned for a small-mV-scale signal.
VitalPatch's raw signal is uncalibrated ADC counts, 2-3 orders of
magnitude larger — at that scale the filter's gain collapses and it
smears every QRS complex into a decaying blob instead of tracking it
(measured on a real segment: peak-to-peak amplitude dropped ~12x, from
~1420 to ~120, after this one step).

**Fix:** the waveform-panel reconstruction now calls
`apply_filter_chain(..., skip_emg_suppress=True)` — display only. This
mirrors a choice the pipeline already makes for R-peak *detection*
(`detect_and_segment` also runs on a Kalman-skipped signal); only
feature extraction uses the full Kalman'd output, and that path was not
touched. Beat classification, rhythm findings, and the risk decision in
each report are computed from the pipeline's own frozen output
(`result`/`saved`) and are byte-identical whether or not this display
function skips Kalman. A note to this effect was added to the report's
own appendix text so a reader isn't left assuming the plotted waveform
is what the classifier saw.
